# v0.3: Error Handling and Logging — Learning Guide

## What this version achieves

The scraper now treats failures as expected events it can explain. It bounds network attempts, checks the shape of API responses before using them, validates individual records, reports duplicates, and communicates whether a run finished completely. It still uses an in-memory collection and writes TSV and PNG outputs; there is no database, API server, or frontend in this version.

The work is on `codex/v0.3-error-handling-logging`. Changes are staged without a commit or push. Two deletions were already staged when this work began (`docs/architecture.md` and `tests/test_scraper.py`); those were preserved. This guide and the new failure-scenario tests use different filenames.

## The architectural rule: recover where recovery makes sense

A row with a broken salary should not stop an entire dataset. A failed dataset should not prevent other datasets from being downloaded. But if discovery fails, there are no datasets to work on, so the run must stop. Each layer therefore has a different responsibility:

| Layer / file | What changed | How it responds |
| --- | --- | --- |
| `client.py` | Shared request helper, timeouts, retries, response validation, resource-link deduplication | Returns usable data or raises `ScraperError` with context |
| `errors.py` | New application-specific exception | Distinguishes expected scraper failures from programming bugs |
| `processing.py` | `clean_record()` validates one row; processing logs aggregate counts | Skips invalid rows and duplicates, continues with valid rows |
| `pipeline.py` | Handles failed datasets and chart errors; reports completion | Continues other datasets, saves usable results, returns a completion boolean |
| `export.py` | Temporary-file export, atomic replacement, TSV quoting | Preserves the previous TSV if writing or replacement fails |
| `reporting.py` | Yearly summaries use logging; chart files close their figures on save failure | Warns when title data is absent; propagates chart errors to the pipeline |
| `Sunshine_List_Scaper.py` | Logging setup and final exception boundary | Returns a meaningful command-line exit code |
| `config.py` | Timeout, retry, backoff, and logging settings | Gives you controls without editing the network implementation |
| `tests/test_error_handling.py` | Offline regression tests with mocked requests | Exercises failures without contacting Ontario or waiting through real retries |
| `README.md` | Run, test, and documentation instructions | Makes the new behavior discoverable |

## Learning try/except

Python raises an exception when an operation cannot complete. Without a matching handler, the exception travels up through the calling functions and eventually ends the program with a traceback.

A `try` block contains the operation that may fail. An `except` block handles a specific kind of failure:

```python
try:
    records = fetch_all_records(api_url, resource_id, **options)
except ScraperError as error:
    logger.error("Skipping failed dataset: %s", error)
    failed_resources.append(resource_id)
    continue
```

Here, `continue` moves to the next resource. It does not pretend that the failed resource succeeded. The pipeline remembers that failure and ultimately returns `False`.

`ScraperError` inherits from `Exception`. It adds no special machinery; its name tells callers that the failure is one the application understands. The client uses `raise ScraperError(...) from error` to translate lower-level failures into useful messages while retaining the original cause for debugging. Resource failures include the resource ID and page offset.

The request helper also uses `else`: that block runs only if the request did not raise an exception. An HTTP error response still counts as a response, so its status must be inspected separately.

The exporter and chart saver use `finally`. That block runs whether an operation succeeds or fails, making it appropriate for removing temporary files and closing figures.

Most handlers are narrow: they catch only errors the layer can recover from. The CLI has one last-resort `except Exception` to log unexpected failures with a traceback and return failure. This is deliberately at the outer boundary; internal programming bugs are not silently ignored. Ctrl+C is handled separately as `KeyboardInterrupt`.

## HTTP status codes, timeouts, and retries

An HTTP status describes the server's response. A timeout or connection failure may occur before a usable HTTP response exists. Those are distinct failure types.

| Situation | Meaning in this scraper | Action |
| --- | --- | --- |
| 200 | Request succeeded at the HTTP level | Use the page; API JSON still needs validation |
| 400 | Bad request | Fail without retrying |
| 401 / 403 | Authentication or access problem | Fail without retrying |
| 404 | Resource not found | Fail without retrying |
| 429 | Too many requests | Retry with bounded backoff |
| 500 / 502 / 503 / 504 | Selected server or gateway failures | Retry with bounded backoff |
| Timeout | Connection or reading waited too long | Retry with bounded backoff |
| Connection error | A connection could not be completed | Retry with bounded backoff |
| Other Requests exception | Another request failure | Translate to `ScraperError`; do not retry |

The helper accepts only HTTP 200. Other statuses outside the retry set fail immediately. Requests follows redirects by default, so the helper inspects the final response.

A successful HTTP response does not guarantee successful CKAN data. Even with status 200, the server may send invalid JSON or a JSON object saying `success: false`.

Defaults in `config.py`:

```python
request_timeout = 30
max_retries = 2
retry_backoff = 1
log_level = "INFO"
```

`max_retries` counts additional attempts. With 2 retries, each page gets at most 3 attempts. The delays are `backoff * 2 ** attempt`: with the default backoff, the first wait is 1 second and the second is 2 seconds. Each retry logs its reason, number, and delay. Permanent errors are not retried because repeatedly asking for a nonexistent resource is unlikely to help.

The timeout is passed to every request, including discovery. A scalar Requests timeout applies to connection and read waiting; it is not a strict total duration for the entire request or scraping run. A slowly streaming response can last longer than 30 seconds. See the [Requests timeout documentation](https://requests.readthedocs.io/en/latest/user/quickstart/#timeouts).

Timeouts must be positive finite numbers, retry counts nonnegative integers, and backoff nonnegative finite numbers. Invalid values become explained scraper failures. The optional page size is also checked to avoid nonsensical pagination.

Retries are safe here because the client makes GET requests to read data. This implementation does not interpret `Retry-After`, add random jitter, or enforce a total run deadline; those are possible later improvements.

## Malformed responses and pagination

Before collecting an API page, the client checks that:

1. The response is valid JSON.
2. Its top level is a dictionary.
3. `success` is exactly `True`.
4. `result` is a dictionary and `result.records` is a list.
5. The batch does not exceed the requested size.
6. A full batch is not identical to the previous full batch.

The last check protects against a server repeatedly returning the previous page while ignoring the next offset. It detects consecutive repeated full pages; it is not a general detector for every possible pagination defect. A batch shorter than the page size ends pagination as before.

A response containing a list with some bad rows is handled differently from a broken response structure: processing can skip individual rows, so a single bad row does not discard the whole resource.

If page two fails after page one succeeded, the function raises rather than returning the partial resource. This avoids silently presenting a partly downloaded dataset as complete. The pipeline discards that resource's fetched rows, records its failure, and continues with other resources. Malformed JSON and schema failures are not retried in this version.

Discovery also fails clearly if it finds no matching resource links. Duplicate resource links are removed using the resource ID, including links whose query strings or trailing slashes differ. The pipeline extracts IDs from the URL path rather than accidentally including a query string.

## Missing fields, unexpected data, and duplicates

`clean_record()` is the new single-row validation boundary. It either returns a normalized record plus its deduplication key or raises an explained validation error. `process_records()` catches row errors and continues.

| Field / situation | Policy |
| --- | --- |
| Row is not a dictionary | Skip it |
| First name, last name, or employer missing or blank | Skip it; these identify a person and employer |
| Year | Accept the existing four field-name variants; require four ASCII digits |
| Salary | Accept `Salary Paid`, with `Salary` as the fallback when the first is absent or `None`; strip dollar signs and commas |
| Missing or unparseable salary | Skip it rather than inventing a zero |
| Negative, NaN, or infinite salary | Skip it to protect sorting and averages |
| Name, employer, title, or year contains a list/dictionary/boolean | Skip it rather than turning structured data into misleading text |
| Job title missing or blank | Keep the record with an empty title, but warn; it still contributes to salary totals |
| Repeated record | Skip it, retain the first UUID, and count it as a duplicate |

Whitespace normalization and case-insensitive identity matching remain. The key contains first name, last name, title, employer, year, and salary. It is stored in a set across the whole run, so duplicates from different resources are removed. This is exact normalized matching, not fuzzy matching: different salaries or titles still produce different keys.

The old `len(person) == 3` company heuristic is replaced by checks for actual required fields. Invalid counts now include all invalid rows, including missing years, rather than only three-field rows. Duplicate counts are reported separately.

This is intentionally stricter than the previous version. Records previously accepted with zero fallback salaries or incomplete identity fields may now be omitted, so output totals and averages can change. The program does not impose a $100,000 threshold or check that a four-digit year is historically plausible; those are separate domain rules.

## Logging levels and how to read them

Each module uses `logging.getLogger(__name__)`. The module name identifies the source of an event; the entry point configures output once. Libraries do not configure logging merely because they are imported.

| Level | Used for |
| --- | --- |
| DEBUG | Individual skipped-row reasons, repeated resource links, and page offsets |
| INFO | Discovery count, per-resource valid/invalid/duplicate counts, yearly summaries, and saved TSV count |
| WARNING | Retrying a request, invalid-row summaries, missing titles, no title-chart data, and user interruption |
| ERROR | Failed resource, incomplete run, output/chart failures, or a run that must stop |
| CRITICAL | Available in Python, but not needed for this command-line scraper |

`INFO` shows INFO and higher-severity events. Set `log_level = "DEBUG"` to include page and row diagnostics; set it to `"WARNING"` to reduce normal progress output. Invalid rows are summarized once per resource at WARNING so large datasets do not produce one warning for every broken row. DEBUG can still be very verbose.

Example message format:

```text
2026-09-30 12:00:00,000 WARNING sunshine_scraper.client: HTTP 503; retry 1/2 in 1.0s (https://...)
```

Logging currently goes to the console through the default stderr handler. There is no persistent log file. Timestamp formatting uses the machine's local logging time. Calls such as `logger.info("Wrote %s records", count)` defer message formatting until needed. `logger.exception()` adds a traceback for unexpected failures; expected failures get shorter messages. See Python's [Logging HOWTO](https://docs.python.org/3/howto/logging.html).

## Output protection and completion status

The exporter first writes a temporary file in the destination directory. It closes that file, then uses `os.replace()` to replace the final TSV. Keeping both files in the same directory keeps replacement on the same filesystem. If writing or replacement fails, the previous TSV remains and the temporary file is cleaned up. Missing output directories are reported; they are not automatically created.

The writer now uses Python's `csv.DictWriter` with a tab delimiter. The six columns remain the same, and ordinary rows keep their familiar TSV representation. Fields containing tabs, quotes, or newlines are quoted correctly; use a TSV-aware reader rather than splitting such records manually on tabs.

| Result | Output behavior | Exit code |
| --- | --- | --- |
| All resources fetched, some individual rows rejected | Export accepted records, log quality warnings | 0 |
| Some datasets fail but others supply valid rows | Export usable rows, explicitly log incomplete coverage | 1 |
| No usable rows, or discovery fails | Leave existing outputs untouched | 1 |
| TSV export fails | Previous TSV remains; stop the run | 1 |
| Chart generation raises an expected file/value error | Keep saved TSV; report chart failure | 1 |
| No accepted rows have a title | Save yearly chart, warn, skip title chart | 0 if resources otherwise succeeded |
| Unexpected exception | Log traceback and stop | 1 |
| User presses Ctrl+C | Log interruption and stop | 130 |

`run()` returns a boolean for completion; the entry point turns that into an exit code. Automation can use the exit code to tell success from failure without searching console text. A successful run means fetching and export completed under these policies, not that every source row was valid.

Chart files are not published atomically as a pair. A failed chart stage can leave a newly written yearly chart alongside an older title chart. Missing title data does not remove an old title chart. Logs and exit codes explain these cases. Atomic replacement protects the TSV from ordinary write failures; it is not a guarantee against every power-loss or filesystem failure.

## Verification and how to run it yourself

Run from the repository root:

```powershell
python -m pip install -r requirements.txt
python Sunshine_List_Scaper.py
python -m unittest discover -s tests -v
```

If using the existing local virtual environment, replace `python` with `.\.venv\Scripts\python.exe`.

The offline tests mock network responses and retry sleeps. They cover transient failures followed by recovery, permanent HTTP errors, exhausted retries, invalid settings, malformed JSON and response structures, pagination, repeated pages, discovery deduplication, bad rows, field fallbacks, duplicate handling, partial runs, empty runs, failed exports, chart failures, and CLI exit codes. Temporary directories isolate generated TSV and PNG files. Error messages and tracebacks during the tests can be expected test fixtures, not failed assertions; look for the final test result.

No new third-party dependency was added. A complete live Ontario scrape was not run, so the tests verify failure handling and coordination without establishing that every current Ontario dataset matches these validation policies. The scraper still stores all fetched/accepted records in memory, and this version adds no resume checkpoints, database, or scheduler.
